# SIRI product UI: portals, design system and data sources

## Routes
| Route | Who | What |
| --- | --- | --- |
| `/login`, `/register` | anyone | Branded sign-in. "Try the demo" opens a demo admin or candidate session (no account needed). |
| `/admin` | admin / recruiter | Overview: four stats, recently created and completed, templates. |
| `/admin/interviews/new`, `/admin/interviews/[id]/edit` | admin | Create/edit: A information, B configuration, C topics (weights must total 100%, question counts must match), D SIRI behaviour, E candidates, F review and publish. Save draft, preview, publish, success screen. |
| `/admin/interviews`, `/admin/interviews/[id]` | admin | Table with status filters and search; view, edit, duplicate, archive/restore; details with assigned candidates and progress. |
| `/admin/reports`, `/admin/reports/[id]` | admin | Report table with search and filters; full report. |
| `/admin/settings` | admin | Configurable performance thresholds and readiness criteria; restore sample data. |
| `/candidate` | candidate | Upcoming, in progress, completed, recent performance. |
| `/candidate/interviews/[id]` | candidate | Brief (topics, difficulty, duration, instructions) and Start. Only assigned, published interviews resolve. |
| `/candidate/interviews/[id]/room` | candidate | Full-screen interview room. |
| `/candidate/reports`, `/candidate/reports/[id]` | candidate | Own reports only. |
| `/interviews/[id]` | candidate | Legacy deep link to a backend interview id, now opening the same live room. `/interviews` and `/createinterview` redirect. |

## Design system
Tokens in `src/app/globals.css` (`@theme`): warm off-white canvas, white surfaces, charcoal ink, earthy green brand, restrained orange accent. Light only, no purple. Primitives in `src/components/ui/` (Button, Badge, form controls, Modal, display: ScoreRing/ScoreBar/Stat/Avatar/Logo). App shell in `src/components/layout/AppShell.tsx` (sidebar on desktop, drawer on mobile). Reports print cleanly (`window.print()` is the PDF download).

## Where data comes from
The app has one data layer (`features/data/DataProvider.tsx`) that picks the source per session. Pages never branch on it.

| Session | Interviews, assignments | Reports | Interview room |
| --- | --- | --- | --- |
| **Real login** (API) | SIRI backend: `/api/interviews` (create, update, publish, archive), `/api/interviews/:id/assignments` | SIRI backend: `/api/reports`, `/api/reports/:sessionId`, built from the stored evaluations | Live voice interview (WebSocket, Deepgram, Vertex, TTS) |
| **Demo** ("Try the demo") | Sample data in the browser (localStorage) | Authored sample reports, and reports generated from the simulated interview | Scripted SIRI, labelled "Simulated" |

Demo and simulated reports are labelled in the UI ("Sample report", "Simulated evaluation"); nothing there is scored by a model.

### What the backend now does for the new UI
- **Interview model**: `status` (draft / active / archived), `code`, `settings` (role, topics with weights and question counts, difficulty, behaviour, personality) and a multi-candidate `assignments` list. Publishing validates that topic weights total 100 and question counts match.
- **Assignments by email**: an admin assigns people by email; a candidate who signs up (or already has an account) with that email sees the interview. Candidates see only their own assignment, never drafts or archived interviews, and an unassigned candidate gets a 404.
- **The settings drive the live interview**: question budget, follow-up limit, clarifications, skip and repeat, interviewer style and the topic order (the backend sets each question's topic, so report topic scores match the configuration). Final scores use the configured topic weights.
- **Status tracking**: an assignment becomes *in progress* when the candidate starts the live session and *completed* (with the session id) when it finishes with scored answers. A completed one never moves back.
- **Reports**: `GET /api/reports` and `GET /api/reports/:sessionId`, scoped to the candidate or the owning recruiter/admin. A report has scores, topic scores (configured topics never asked are "not covered"), question-by-question evaluations, strengths with quoted evidence, and improvements and a plan derived from the stored evaluations.
- **Not generated by the backend, and shown as such rather than invented**: communication assessment, "a stronger approach" text, study resources and time estimates.

### To use it for real
Set `AUTH_ENFORCED=true` and `JWT_SECRET` / `WS_TOKEN_SECRET`, create an admin with `node scripts/create-admin.js`, sign in on `/login` with real accounts, and have candidates register with the email they were assigned. Without `AUTH_ENFORCED` the API is open and not scoped per user.

## Verification
- Server: 225 tests. Client: 111 tests, type-check, lint, production build.
- End to end against a real isolated backend (auth enforced, throwaway MongoDB, real Gemini and Google TTS): real accounts; a configured interview with assignment by email; the visibility rules; a live interview that followed the configured topics and ended at the configured question count; the assignment moved to completed with the session id; the report endpoints; another candidate refused; and a second session did not move the completed assignment back.
- **Not verified**: the screens in a browser (the browser extension was unavailable), speech-to-text, and the microphone path.

## Known limits
- Invitations are not emailed; an assignment is a record that matches on email.
- No progress percentage for a live interview in progress (the backend does not track it); the UI says "In the interview now".
- Editing an interview that candidates have already started changes the settings for new sessions only.
- The scoring thresholds and readiness criteria are kept in the browser (they only change how a report is labelled).
